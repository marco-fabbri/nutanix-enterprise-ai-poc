# Nutanix Enterprise AI 2.8 PoC — Runbook

Operational reference for the single-node NAI 2.8 installation produced by
this repository. It covers what the installer leaves on the VM, how to reach
each component, and the commands you need on day two. VM provisioning and
external networking are outside the scope of the installer.

Placeholders: `<VM_IP>` is the VM address (`ansible_host`), `<SSH_USER>` the
account in the inventory, `<NAI_URL>` the address printed at the end of the
playbook (`https://<VM_IP>/` in the default TLS mode).

---

## 1. The VM

### 1.1 Baseline

| Item | Value |
|---|---|
| OS | Ubuntu Server 24.04 LTS, x86-64 |
| vCPU / RAM | 16 / 48 GiB dedicated (no ballooning) |
| Disk | 150 GiB on the root filesystem |
| Swap | Disabled by the installer (fstab entry commented out) |
| Kernel | `overlay`, `br_netfilter` loaded; bridge-nf and ip_forward sysctls set |
| Packages added | curl, wget, jq, git, socat, nfs-common, open-iscsi, nfs-kernel-server, ca-certificates, tar, haproxy |

### 1.2 SSH access

```bash
ssh <SSH_USER>@<VM_IP>
sudo -k -n true && echo "passwordless sudo OK"
```

The installer copies the cluster kubeconfig to `/home/<SSH_USER>/.kube/config`,
so `kubectl` works for that account without sudo.

## 2. Kubernetes and storage

| Item | Value |
|---|---|
| Distribution | RKE2, pinned release tag in `rke2_version` (Kubernetes 1.35) |
| CNI | canal; `rke2-ingress-nginx` disabled (Envoy Gateway is the ingress) |
| Kubeconfig (root) | `/etc/rancher/rke2/rke2.yaml` |
| Binaries | `/var/lib/rancher/rke2/bin/{kubectl,crictl,ctr}` symlinked into `/usr/local/bin` |
| Service | `rke2-server.service` |
| Helm | pinned in `helm_version` |

Storage classes:

| Class | Mode | Backing |
|---|---|---|
| `local-path` (default) | RWO | Directories under `/opt/local-path-provisioner` on the VM disk |
| `nai-nfs-storage` | RWX | Local NFS export `/srv/nfs/nai-shared`, exported to `<VM_IP>/32` only |

MinIO (when `deploy_minio=true`):

| Item | Value |
|---|---|
| Namespace | `minio-system` |
| S3 endpoint (in-cluster) | `http://minio.minio-system.svc.cluster.local:9000` |
| Console (in-cluster) | port 9001 on the same service |
| Credentials | `minio_root_user` / `minio_root_password` from the inventory, stored in Secret `minio-root` |
| Volume | PVC `minio-pvc`, `minio_storage_size` (default 50Gi) on `local-path` |

MinIO is not exposed outside the cluster. To reach the console from your
computer, tunnel through SSH to a port-forward running on the VM, then open
`http://localhost:9001`:

```bash
ssh -L 9001:127.0.0.1:9001 <SSH_USER>@<VM_IP> kubectl -n minio-system port-forward svc/minio 9001:9001
```

Changing the MinIO credentials after the first start requires a restart with
`MINIO_FORCE_NEW_KEYS=yes` or a fresh volume; the image keeps the keys from
its first initialisation.

## 3. Networking, ingress and TLS

### 3.1 Traffic flow

```
Client
  │  TCP 443 / TCP 80
  ▼
HAProxy on the VM (<VM_IP>)            /etc/haproxy/haproxy.cfg, TCP mode
  │  forward to the Envoy Gateway service, resolved through the cluster DNS
  ▼
Envoy Gateway (envoy-gateway-system)    TLS termination with Secret nai-tls-cert
  │
  ▼
oauth2-proxy → NAI UI / NAI API (nai-system)
```

HAProxy is generated by the `ingress` phase. The backend is the Envoy Gateway
service name resolved through CoreDNS (`resolvers cluster` in
`haproxy.cfg`), so a recreated service with a new ClusterIP is picked up
without re-running anything. Re-run `./deploy.sh install --tags ingress` only
if the service name itself changes (a different Gateway name or namespace).

### 3.2 `tls_mode=selfsigned` (default)

The nai-core chart creates in `nai-system` a self-signed root
(`Issuer/selfsigned-root` → `Certificate/root-ca` → Secret `ca-key-pair`) and
an `Issuer/ca-issuer` backed by it. The installer requests
`Certificate/nai-tls-cert` from `ca-issuer` with `ipAddresses: [<VM_IP>]` and,
when `nai_fqdn` differs from the IP, `dnsNames: [nai_fqdn]`. The Gateway
listener references Secret `nai-tls-cert`.

Browsers warn because the root CA is private. To trust it on a workstation,
export it and import it into the OS or browser trust store:

```bash
kubectl -n nai-system get secret ca-key-pair -o jsonpath='{.data.ca\.crt}' | base64 -d > nai-root-ca.crt
```

### 3.3 `tls_mode=letsencrypt`

- `ClusterIssuer/letsencrypt-prod`, ACME HTTP-01 solved through an HTTPRoute
  attached to `Gateway/nai-ingress-gateway`.
- CoreDNS (`rke2-coredns-rke2-coredns` ConfigMap) maps `nai_fqdn` to `<VM_IP>`
  so cert-manager's self-check resolves the name to the VM from inside the
  cluster.
- Prerequisite: public DNS for `nai_fqdn` and TCP 80/443 forwarded to the VM
  before the run. The playbook waits up to `tls_ready_timeout` (default 300s)
  for the certificate.

### 3.4 `tls_mode=provided`

The installer writes Secret `nai-tls-cert` (type `kubernetes.io/tls`) from
`tls_cert_file` and `tls_key_file` read on the Ansible controller. No
cert-manager resources are involved and no renewal happens. To rotate the
certificate, update the files and re-run `./deploy.sh install --tags nai`.

### 3.5 Checking the certificate

```bash
kubectl -n nai-system get certificate nai-tls-cert
kubectl -n nai-system describe certificate nai-tls-cert   # Events explain a stuck request
openssl s_client -connect <VM_IP>:443 -servername <VM_IP> </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -ext subjectAltName
```

In `provided` mode there is no Certificate object; inspect the Secret instead:

```bash
kubectl -n nai-system get secret nai-tls-cert -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -subject -issuer -enddate
```

## 4. Authentication and onboarding

| Item | Value |
|---|---|
| URL | `<NAI_URL>` |
| Bootstrap user | `admin` |
| Bootstrap password | `Nutanix.123` |

On first login NAI enforces a password change and EULA acceptance. The
installer does not alter that flow.

Licensing: the playbook prints the cluster UID (`kubectl get ns kube-system -o
jsonpath='{.metadata.uid}'`). On the Nutanix portal go to Licenses → Manage
Licenses → Manage NAI/NKP, register the cluster with that UID, generate the
key and paste it under Settings → Licensing in the NAI console.

## 5. Cheat sheet

All commands on the VM. `kubectl` works for `<SSH_USER>` through the copied
kubeconfig; prefix with `sudo KUBECONFIG=/etc/rancher/rke2/rke2.yaml` when
running as another user.

```bash
# Cluster health
kubectl get nodes -o wide
kubectl get pods -A | grep -v Running

# NAI components
kubectl -n nai-system get pods
kubectl -n nai-system logs deployment/nai-api -c nai-api --tail=100 -f
kubectl -n nai-system logs deployment/iam-user-authn -c iam-user-authn --tail=100 -f
kubectl -n envoy-gateway-system logs deployment/envoy-gateway --tail=100 -f

# Database cluster health (CloudNativePG)
kubectl -n nai-system get cluster nai-db-iep

# Ingress path
sudo systemctl status haproxy
kubectl -n envoy-gateway-system get svc -l gateway.envoyproxy.io/owning-gateway-name=nai-ingress-gateway

# Helm releases installed by the playbook
helm list -A
```

Re-running phases from your computer:

```bash
./deploy.sh check                          # preflight only
./deploy.sh install --tags nai,ingress     # redeploy NAI charts and refresh HAProxy
./deploy.sh install --tags storage         # storage provisioners and MinIO
./deploy.sh install -e deploy_minio=false  # one-off override of any default
```

## 6. Troubleshooting

| Symptom | Where to look |
|---|---|
| Preflight fails on OS, credentials, charts or ports | The message names the missing input. `nai_skip_os_check=true` bypasses the Ubuntu 24.04 and x86-64 checks only. |
| RKE2 install fails to download | The VM needs outbound HTTPS to `get.rke2.io`, `github.com`, `raw.githubusercontent.com`, `get.helm.sh`, `charts.jetstack.io`, `cloudnative-pg.github.io`, `kubernetes-sigs.github.io`, `prometheus-community.github.io`, `index.docker.io`, `registry.k8s.io`, `quay.io` and `ghcr.io`. The pinned tag avoids the release-channel service entirely. |
| `nai-operators` or `nai-core` Helm timeout | `kubectl -n nai-system get pods`; `ImagePullBackOff` means wrong Docker Hub credentials (secret `nai-regcred`), `Pending` usually means the VM is under the memory baseline. |
| `certificate/nai-tls-cert` never Ready | `kubectl -n nai-system describe certificate nai-tls-cert`. In `letsencrypt` mode also check `kubectl -n nai-system get challenges`, DNS and the 80/443 forwarding. |
| Console unreachable on 443 | `sudo systemctl status haproxy` and `echo "show servers state" \| sudo socat stdio /run/haproxy/admin.sock` are the first checks; if the Envoy service was renamed, `./deploy.sh install --tags ingress`. |
| MinIO pod `ImagePullBackOff` | The image is pinned to a Bitnami legacy tag; verify it is still published or set `deploy_minio=false`. |
| `helm upgrade` of nai-core fails with `conflict occurred while applying object ... EnvoyProxy ... conflicts with "kubectl-patch"` | The EnvoyProxy was edited with `kubectl patch` outside Helm. Run the nai-core `helm upgrade` command from `ansible/roles/nai_poc/tasks/06_deploy_nai.yml` once by hand adding `--force-conflicts` so Helm takes the fields back, then re-run the playbook. |

## 7. Reinstalling from scratch

The installer is idempotent for its own phases, but it does not uninstall.
For a clean slate, destroy and recreate the VM from your platform, then run
`./deploy.sh install` again. On an existing VM, `rke2-uninstall.sh` removes
the cluster; the volume data under `/opt/local-path-provisioner` and
`/srv/nfs/nai-shared`, the NFS export, HAProxy and the packages remain.

Changing `rke2_version` re-runs the installer script and restarts
`rke2-server` on the existing node; check the RKE2 upgrade notes for the
version jump first. Changing `docker_token` needs `--tags prereqs` to refresh
the registry secret.
